# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev      # Next.js dev server on :3000
npm run build    # Production build (also type-checks)
npm run start    # prisma migrate deploy && next start -- runs pending migrations before serving
npm run lint     # ESLint (flat config, includes TypeScript + React Compiler rules)
```

`postinstall` runs `prisma generate` automatically, so a fresh `npm install` always has a matching client.

## Architecture

Next.js 16 App Router, deployed on Railway (not Vercel) as `app.reyse.co.uk` — the admin dashboard for Reyse.

### Auth

NextAuth v4, Google OAuth, JWT sessions, single hardcoded admin-email allowlist in `src/lib/auth.ts` — no roles table. Route protection is `src/proxy.ts` (Next 16 renamed `middleware.ts` → `proxy.ts`; the old `next-auth/middleware` wrapper isn't a valid proxy export on 16, so it's written directly against `getToken`). The matcher protects everything except `/login`, `/api/auth/*`, `/api/public/*`, and static assets. `src/app/admin/layout.tsx` does a second, server-rendered session check so a protected page never flashes unauthenticated.

**Docs-drift note (corrected 30 July 2026):** this file previously described dashboard routes as living under a `(dashboard)/` route group. The actual code has always used `src/app/admin/*` (Morgan's call, 22 July 2026 — see `src/lib/nav.ts`'s comment). Every path reference below is corrected to match the real filesystem; if you find another `(dashboard)/...` reference anywhere in this file, it's stale, not a second real route group.

### Database — Prisma 7, driver adapters are mandatory

Prisma 7 changed connection config significantly from v6 — **do not** put `url = env("DATABASE_URL")` in the `datasource` block in `schema.prisma`; the CLI rejects it (`P1012`, "no longer supported in schema files"). Instead:
- `prisma.config.ts` carries the connection string for the CLI (`migrate`, `generate`, `studio`) via `datasource: { url: process.env["DATABASE_URL"] }`.
- The generator is `provider = "prisma-client"` (not the old `prisma-client-js`), output to `src/generated/prisma` (gitignored, regenerated on every install). **The import path is `@/generated/prisma/client`, not `@/generated/prisma`** — there's no root `index.ts`, only `client.ts`.
- At runtime, `PrismaClient` requires a driver adapter — there is no more "just works from schema" direct connection. `src/lib/db.ts` constructs `new PrismaPg({ connectionString: process.env.DATABASE_URL })` from `@prisma/adapter-pg` and passes it as `new PrismaClient({ adapter })`. Omitting the adapter fails at the `new PrismaClient()` call site with a TypeScript error (constructor expects 1 required arg), not a runtime surprise.

Migrations are generated offline (this sandbox can't reach Railway's Postgres directly — only HTTPS egress works, not raw TCP): `npx prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script > prisma/migrations/<name>/migration.sql`, committed, then applied automatically on deploy via the `start` script's `prisma migrate deploy`.

### Enquiries feature

Captures every lead (website contact form, WhatsApp, Instagram, Facebook, manual) into one Postgres-backed pipeline — status tracking (New/Contacted/Won/Lost), notes, soft-delete with restore (`deletedAt`, never a hard delete), and stats (7/30-day volume, avg response time, win rate, top channel).

- `prisma/schema.prisma` — `Enquiry` model, `EnquiryChannel`/`EnquiryStatus` enums, indexed on `status`, `channel`, `deletedAt`, `createdAt`.
- `src/lib/enquiries.ts` — `validateEnquiryInput()`, shared between the public and dashboard creation paths so they can't validate differently.
- `src/app/api/public/enquiries/route.ts` — unauthenticated (no session exists on the caller's side), protected instead by a shared-secret header (`x-api-key` matched against `INTERNAL_API_SECRET`). This is what Reyse-Website's `api/contact.ts` calls server-to-server, independent of that form's Resend email — either path failing still leaves the enquiry captured by the other. Requires `INTERNAL_API_SECRET` to be set to the *same* value on both this app's Railway service and the Reyse-Website Vercel project; the route fails closed (500) if its own copy is unset, and 401s on the wrong or missing key.
- `src/app/api/enquiries/**` — session-protected CRUD (list+filter, manual/test add, PATCH status/notes, soft-delete, restore) for the dashboard itself. List is capped at 200 rows (`take: 200`, no pager UI yet).
- `src/app/api/enquiries/stats/route.ts` — always filters out `isTest` and soft-deleted rows so test/deleted data can't skew real numbers. `last7DaysCount` and 30-day `volumeByDay` bucketing are computed server-side deliberately (not with `Date.now()` in a component during render) — React's purity/`set-state-in-effect` lint rules flag date-dependent calculations done at render time.
- `src/app/admin/enquiries/page.tsx` + `src/components/enquiries/*` — the UI. Data fetching is a plain `useEffect` + `fetch` (no query library in this app yet); `react-hooks/set-state-in-effect` flags this pattern regardless of await timing since it's aimed at nudging toward Suspense/query libraries — there's a scoped `eslint-disable` on that one line with the reasoning inline.

### Env vars this feature needs

- `DATABASE_URL` — Postgres connection string (Railway).
- `NEXTAUTH_SECRET`, Google OAuth client ID/secret — existing auth requirements, unrelated to this feature.
- `INTERNAL_API_SECRET` — shared secret for `/api/public/enquiries`, must match Reyse-Website's Vercel env var of the same name.

### Social media automation

Generates and posts real single/carousel content to Reyse's own Instagram and Facebook accounts (promoting the business itself, not a per-client feature) — captions and hashtags via Claude, images either AI-generated photography (Replicate) or branded template graphics (rendered in-process), reviewed in a queue before anything goes live by default. Built 22 July 2026.

**Why this shape:** the old `reyse` repo had three separate, never-reconciled systems for this (a single-post pipeline, a carousel pipeline, a story pipeline), each with its own image source, its own storage backend, and even a different env var for the same Instagram account — explicitly judged not good enough. This is one unified pipeline instead: one content-generation path, one image-generation path (that internally chooses AI photography or a template per post), one Graph API client, one scheduler.

- `prisma/schema.prisma` — `SocialPost` (one row per platform per post; two rows sharing a `groupId` are a cross-posted Instagram+Facebook pair, generated together with identical content but published/edited independently), `SocialPostImage`, `SocialAsset` (image bytes stored in Postgres, not external blob storage — see below), `SocialSettings` (singleton row, publishing mode + cadence), `AiUsageLog` (generic, reused by any future feature with AI/paid-API costs).
- `src/lib/social/pillars.ts` — the six content pillars (Education, Tips, Promotion, Social proof, Behind the scenes, News) and the rotation order the scheduler advances through. Social proof and Behind the scenes are explicitly instructed never to fabricate a customer name, quote, or stat — Reyse's old website had fake testimonials and they were removed for exactly that reason; this is a standing constraint, not a one-off note.
- `src/lib/social/captionGenerator.ts` — Claude (`claude-opus-4-8`, adaptive thinking, `effort: "high"`, structured JSON output via `output_config.format`) grounded in the **same `ChatKnowledge` table the live chat widget uses** — one shared source of truth for pricing/feature facts across both surfaces, edited from either the Live Chat or Social admin page (same modal, same underlying content). System prompt encodes the caption structure (hook/value/CTA), the no-em-dash / no-AI-cliché brand voice rules, and 3-5 hashtags.
- `src/lib/social/contentValidation.ts` — an automated quality gate (em dash check, banned AI-slop phrases, hashtag count, caption length) run on every generation; a failure triggers one retry with the specific feedback appended before falling through to human review regardless. Not a replacement for the review queue, a first line of defence so obviously-off-brand output doesn't even reach it looking finished.
- `src/lib/social/imageGenerator.ts` + `templateRenderer.tsx` + `fonts.ts` — chooses AI photography (Replicate, `black-forest-labs/flux-1.1-pro`, a consistent camera/lighting style suffix appended to every prompt to avoid "AI slop" and keep the whole feed visually consistent) for Promotion/Social proof/Behind-the-scenes, or a branded template graphic (rendered server-side via `next/og`'s `ImageResponse`, 1080x1350, Reyse's actual brand tokens from Reyse-Website's `index.css`) for Education/Tips (carousels) and News. AI photography silently falls back to a template if Replicate is unavailable or `REPLICATE_API_TOKEN` isn't set — a missing/dead image-gen key degrades the image style, it never blocks a post. **Fonts are bundled via `@fontsource` and read from `node_modules` at render time, not fetched from Google Fonts over the network** — an earlier version fetched fonts.googleapis.com per render and it silently failed in testing (`next/og`'s `ImageResponse` throws "No fonts are loaded" if the font array ends up empty), which would have crashed image generation in production on any network hiccup. Confirmed working via a real rendered test image, not just a type-check.
- `src/lib/social/graphApi.ts` — Meta Graph API client. Instagram: single post is container-then-publish; carousel is child containers (`is_carousel_item`) → parent `CAROUSEL` container → publish, with status polling (`FINISHED`/`ERROR`/`EXPIRED`) at each step, matching the confirmed-working flow from the old repo's carousel code. Facebook: single post is `POST /{page-id}/photos` directly; multi-photo is upload-each-unpublished-then-attach-to-one-feed-post (Facebook has no native organic "carousel" post type). Also implements genuine delete (`DELETE /<id>` on both platforms, confirmed actually supported, not assumed) so "undo" on an already-published post can really remove it live, not just hide the local record.
- `src/app/api/public/social/assets/[id]/route.ts` — public, unauthenticated image-serving route (Meta's servers fetch images by plain HTTPS URL; same trust model as the live-chat SSE stream, an unguessable cuid is the access boundary). Images are stored as `Bytes` directly in Postgres rather than a separate blob store (Azure Blob, S3) — one less external dependency that could be misconfigured with nobody around to fix it, and the old repo's carousel system already used the same "Postgres as blob store" pattern successfully.
- `src/lib/social/scheduler.ts` + `src/instrumentation.ts` — a `setInterval` started from Next's `register()` boot hook, checking every 5 minutes. Confirmed as the old `reyse` backend's actual working mechanism for its Instagram autopilot (read directly from its source), not guessed — its own `CRON_JOBS.md` documented a *different*, unused mechanism, a docs/code drift this rebuild's CLAUDE.md is specifically trying not to repeat. Only makes sense on Railway's persistent Node process, not Vercel's stateless functions. Generates a new cross-posted pair on a cadence derived from `SocialSettings.postsPerWeekInstagram`; publishes anything `SCHEDULED` and due **regardless of publishing mode** — reaching `SCHEDULED` already means approval happened (human, in review-queue mode; automatic, in autonomous mode), so gating the publish step on mode too would mean an approved post in review-queue mode never actually goes out.
- `src/app/admin/social/page.tsx` (nav label "Social") + `src/components/social/*` — review queue UI: filter by status/pillar, a card grid with real image thumbnails (not a text table — reviewing photos and carousels needs to see them), a detail modal with editable caption/hashtags and full status-transition controls (approve & schedule / reject / publish now / undo / delete / restore), a settings panel (publishing mode toggle, cadence), and a manual "Generate now" button that bypasses the cadence timer.
- **Publishing mode is the one safety-critical control** (`SocialSettings.publishingMode`): `REVIEW_QUEUE` (default) means every generated post sits as a draft until a human approves it; `AUTONOMOUS` means the pipeline auto-approves and the scheduler publishes with no human ever looking at it. Defaults to `REVIEW_QUEUE` deliberately — this posts to a live business's real public social presence, and the first batch should be seen before anything goes out unsupervised.
- `src/lib/aiUsageLog.ts` + `/api/analytics/ai-usage` + `src/app/admin/analytics/page.tsx` — generic AI/paid-API cost logging (modelled on the old backend's `AiUsageLog`, minus the mess: no per-tenant field, one shared table for every feature) and a real usage summary replacing the Analytics placeholder. First feature to actually build this — it was flagged as a gap when the live chat widget shipped ("whichever feature needs it first should build it"). Image-generation cost isn't priced (Replicate bills per-second of compute, not per-image, so there's no honest fixed cost to log) — image calls show as counts, not a dollar figure; check the Replicate dashboard for actual spend.

**Env vars this feature needs:**
- `ANTHROPIC_API_KEY` — same key the live chat widget uses; should already be set (it originated on this Railway service during the 20 July variable migration, before being copied to Reyse-Website's Vercel project) but **not directly re-confirmed present for this feature** — verify after deploy.
- `REPLICATE_API_TOKEN` — optional. Listed in `How Reyse Works.md` as present on this Railway service but "never confirmed as used or unused" before now. If missing or invalid, AI photography silently falls back to template graphics; nothing breaks.
- `INSTAGRAM_ACCESS_TOKEN`, `INSTAGRAM_USER_ID` — required to actually publish to Instagram. **Not confirmed to exist on this Railway service** — genuinely unknown at build time, unlike `ANTHROPIC_API_KEY`/`REPLICATE_API_TOKEN`. Without them, generation and review work fully; any publish attempt fails with a clear reason shown on the post (`FAILED` status), nothing crashes.
- `FACEBOOK_PAGE_ACCESS_TOKEN`, `FACEBOOK_PAGE_ID` — same as above, for Facebook.
- `PUBLIC_BASE_URL` — optional, defaults to the working `reyse-app-production.up.railway.app` Railway URL (same `app.reyse.co.uk`-isn't-attached-yet workaround used everywhere else in this codebase). Used to build the image URLs handed to Meta's Graph API.

### Lead Generation

Finds prospective clients (independent UK holiday-let owners with their own direct-booking website, per `docs/lead-gen.md`'s ideal-customer-profile) via two Google search channels, classifies and enriches each candidate, and verifies the contact details it finds before they're usable. Built 30 July 2026, replacing the old `reyse` backend's version — Morgan's own verdict on that one: "did what I wanted but nowhere near as well." The full weakness-by-weakness comparison lives in `docs/lead-gen.md`; the short version is it had almost no real duplicate protection (URL-string uniqueness only, so http/https/www variants of the same site duplicated), MX-only email "verification" that couldn't catch catch-all domains, and a real bug where its own "excluded from export" promise silently didn't hold. This rebuild fixes all three directly, not just re-implements the same design.

- `prisma/schema.prisma` — `Lead` (the one table; `domain` is `@unique` and *normalized* — no protocol/www/trailing-slash — so it's a real dedup key, not a raw-string one), `LeadCollection` (optional grouping for one search run/area), `LeadSearchUsage` (daily Google API call counters, not a cost figure — see below), enums `LeadClassification`/`LeadSource`/`LeadEnrichmentStatus`/`LeadEmailVerification`/`LeadInstagramVerification` (all real Postgres enums, not free strings, `@@map`'d `ra_lead_*` per this schema's shared-database convention).
- **Dedup is enforced before any paid/metered call, not just at the database write.** `src/app/api/leads/search/route.ts`'s `alreadyKnown()` checks the normalized domain against every lead ever saved — found before, excluded, contacted, doesn't matter — before spending a Claude classification call on it. A lead row is never hard-deleted (only `excluded: true`), specifically so this memory never resets; excluding a lead and re-finding it later both leave the dedup key intact.
- **Two search channels.** `src/lib/leadgen/places.ts` (Google Places Text Search + Details, biased to real lat/lng coordinates from `src/lib/leadgen/searchTerms.ts`'s `UK_REGIONS` list rather than a free-text place name — genuine map search, needs a billing-enabled Google Cloud project, Morgan's confirmed call was to add the card since realistic usage should stay inside the $200/month free credit; `GOOGLE_PLACES_API_KEY` confirmed NOT present on this Railway service, checked 30 July 2026) and `src/lib/leadgen/customSearch.ts` (Google Custom Search JSON API, genuinely free up to 100 queries/day, no billing card, quota tracked in `LeadSearchUsage` via `src/lib/leadgen/usage.ts` so it stops itself before the free tier runs out and starts costing money; `GOOGLE_CUSTOM_SEARCH_KEY`/`GOOGLE_CUSTOM_SEARCH_CX` **do** already exist on this Railway service — carried over from the old backend during the 20 July variable migration and left as "uncertain, not removed" at the time, confirmed working 30 July 2026. Code reads `GOOGLE_CUSTOM_SEARCH_CX`, not `GOOGLE_CSE_ID` — matches the variable name already there instead of asking for a rename). Search results missing an env var return `503` from the route with the exact env var name in the body rather than crashing, same pattern as the missing Instagram/Replicate tokens elsewhere in this app.
- `src/lib/leadgen/classify.ts` — one Claude Haiku (`claude-haiku-4-5-20251001`) call per candidate site, reading its homepage text against `src/lib/leadgen/icp.ts`'s condensed ideal-customer-profile, returning `INDEPENDENT`/`PLATFORM`/`IRRELEVANT` plus a one-line reason. Explicitly instructed to prefer `IRRELEVANT` over `INDEPENDENT` when unsure — "high quality leads only" means false positives cost more than false negatives here. A homepage that can't be fetched at all becomes `ERROR` (unclassified), kept distinct from a genuine `IRRELEVANT` verdict.
- `src/lib/leadgen/enrich.ts` — regex-first extraction (email/phone/Instagram/LinkedIn/Facebook from the homepage, falling back to a same-site "contact" page if fewer than 2 fields found), then a Claude Haiku call only to fill genuine gaps (missing fields, contact name, or the outreach personalisation line) — mirrors the old backend's waterfall but fixes its permanent-failure behaviour: one retry on a transient homepage fetch failure (`src/lib/leadgen/fetchSite.ts`) before a lead is marked `FAILED`, and `src/app/api/leads/enrich/route.ts` runs a small concurrency pool (4 at once) instead of one-at-a-time with a fixed sleep. Cross-lead email/Instagram-handle collisions are dropped (not just hidden) via a `findFirst` check against every other `Lead` row.
- **Email verification is automatic, not a disconnected manual button** (the old tool's was opt-in and never wired into the enrichment pipeline at all). `src/lib/leadgen/verifyEmail.ts`: MX lookup first (`node:dns/promises`), then a best-effort raw SMTP probe (`node:net`, port 25, `RCPT TO` without ever sending `DATA`) that also probes a random nonexistent address at the same domain in the same session (via `RSET` between probes) specifically to catch **catch-all domains** — the old tool's MX-only check couldn't tell "this exact mailbox exists" from "this domain accepts everything." `RISKY` is a real, distinct state for exactly that ambiguity. **Whether Railway allows outbound port 25 was unconfirmed at build time** (many hosts block it to stop spam) — if the SMTP probe can't connect, this honestly falls back to `RISKY` (MX exists, mailbox unconfirmed) rather than claiming `VALID` on a check that never actually ran. Verify after deploy: search a lead with a known-real email and check whether `emailVerification` lands on `VALID` (SMTP worked) or stays `RISKY` (port likely blocked, in which case MX-only is the real ceiling here).
- `src/lib/leadgen/verifyInstagram.ts` — an unauthenticated fetch to the profile URL (no official API for this without app review). Only a genuine `404` counts as `INVALID` and only a genuine `200` counts as `VALID`; a blocked/rate-limited/timed-out request stays `UNVERIFIED` rather than the old tool's "any error = probably fine" logic, which wasn't actually evidence of anything.
- `src/app/admin/leads/page.tsx` + `src/components/leads/*` — search panel (map/web toggle, region+town picker from `UK_REGIONS`, search-term picker from `SEARCH_TERMS`, optional collection), a live SSE progress feed while a search runs, a result list with inline-editable contact chips and verification badges, per-lead re-enrich/exclude actions, an "enrich pending" bulk action, and CSV export. Outreach/sequence tracking (the old tool's DM/email cadence tracker) was deliberately not carried over — Morgan's steer, leads just get a status here, no cadence tooling.
- `src/app/api/leads/export/route.ts` — the one and only read path for CSV export, filters on `excluded: false` directly on the `Lead` row. This is the specific fix for the old tool's real bug: its "blocked contacts" list was a second table that the export code never actually checked, so excluded contacts leaked into CSVs despite the UI promising otherwise. Here there's one flag and one code path, so that drift can't recur.

- `GOOGLE_PLACES_API_KEY` — Google Places API (Text Search + Details). **Not set on this Railway service** (confirmed 30 July 2026) — map search returns a clear 503 until it's added. Needs a Google Cloud project with billing enabled; realistic usage should stay inside the $200/month free credit.

No billing account needed; genuinely free up to 100 queries/day, enforced by `LeadSearchUsage`.

### Email Assistant

Full access to Morgan's own Gmail (`morgan.king@reyse.co.uk`) — not a per-client feature. Reads the inbox, organises it into folders (Gmail labels) with full autonomy, and will draft replies in a later phase (never send). Requested 30 July 2026, phase 1 (connect + read + organise) built the same day; drafts and a chat panel are deliberately out of scope for phase 1. Extended 31 July 2026, still within phase 1: real move (not just add) between folders, plus a backfill sweep through the whole existing mailbox — Morgan's original ask covered "take mail out of a folder and put it in another" and "everything I already have," not just new arrivals, and the first build only handled the latter.

**Why a dedicated OAuth client:** a second, separate Google OAuth client ("Reyse Mail Assistant", Web application type) lives in the same Google Cloud project (`managing-emails-491718`) as the one `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` use for dashboard sign-in — kept deliberately apart so nothing this feature does can affect login. Audience is set to **Internal** (the Google Workspace org for `reyse.co.uk` was confirmed live, 30 July 2026), which matters for a real reason: an **External + Testing** OAuth app only issues refresh tokens that expire after 7 days, and Gmail's scopes are Google-classified as restricted, meaning fixing that properly would mean a Google verification review. Internal skips both entirely — no expiry, no verification — because it's Workspace-only and single-user by construction.

A prior attempt at this exact feature exists and was checked before building: an OAuth client called "Email Manager" (Desktop type, 29 March 2026) sits in the same Google Cloud project, built for an n8n workflow Morgan tried and abandoned. Not reused — wrong OAuth type for a server-side web app in any case. See `Email Assistant.md` in the vault for the full history.

- `prisma/schema.prisma` — `MailAccount` (singleton row, id `"singleton"`; holds the AES-256-GCM-encrypted Gmail refresh token, not plaintext, plus `backfillStatus`/`backfillPageToken` tracking the mailbox sweep below), `MailActivityLog` (one row per organising action, what the Mail page's activity feed reads from) + `MailActivityAction` enum (`MESSAGE_FILED` for a first-time folder, `MESSAGE_MOVED` for a real change).
- `src/lib/mail/crypto.ts` — `encryptToken`/`decryptToken`, AES-256-GCM keyed by `MAIL_TOKEN_ENCRYPTION_KEY`.
- `src/lib/mail/googleClient.ts` — the dedicated OAuth2 client (`GMAIL_CLIENT_ID`/`GMAIL_CLIENT_SECRET`, distinct from the sign-in ones), consent URL generation, code-for-tokens exchange, and `getAuthorizedGmailClient()` which loads and decrypts the stored refresh token into a ready-to-use `gmail_v1.Gmail` client. Listens for Google's rare refresh-token rotation and persists it if it happens.
- `src/lib/mail/labels.ts` — every actual Gmail-side folder operation (`listFolders`, `createFolder`, `renameFolder`, `deleteFolder`, `refileMessage`), each one writing its own `MailActivityLog` row in the same place the change happens. `isFolderLabel`/`listFolders` treat only Gmail's `type: "user"` labels as folders — system labels (INBOX, SENT, CATEGORY_*, UNREAD, ...) are never created/renamed/deleted/removed. `refileMessage` diffs a message's current folders against where it should be and does a real move (`addLabelIds` + `removeLabelIds` in one call) — it's a no-op (no API call, no log entry) if the message is already correctly filed. Deleting a folder only removes the label; the underlying messages are never deleted, so it's always recoverable.
- `src/lib/mail/organizer.ts` — `classifyMessages` (Claude, `claude-opus-4-8`, structured JSON output, same pattern as `captionGenerator.ts`) decides which folder(s) a message belongs in, strongly preferring an existing folder over inventing a new one. Folder-name matching is case-insensitive and trimmed specifically to stop the model creating near-duplicate folders ("Finance" vs "finance") across separate ticks. `organizeMessages` is shared by both the ongoing new-mail job and the backfill sweep below — an `InboxMessage` carries its `currentFolders`, so the same function handles "never filed before" and "already somewhere, might need to move" identically.
- `src/lib/mail/scheduler.ts` + `src/instrumentation.ts` — two jobs on one 5-minute tick (same pattern as the social scheduler, registered alongside it):
  - **New-mail sync** — deliberately conservative, only touches messages with no folder on them yet, so it never fights a manual filing choice Morgan made between ticks. Uses Gmail's incremental History API once a `historyId` cursor exists; falls back to a bounded fresh inbox scan both on first run and if the cursor has expired (Gmail only retains ~1 week of history).
  - **Backfill sweep** — Morgan's 31 July ask: reconsider the *entire* existing mailbox, not just new arrivals, and genuinely move things rather than only add. Pages through everything except Sent/Drafts/Trash/Spam/Chat (`backfillStatus`/`backfillPageToken` on `MailAccount` track progress across ticks), reclassifying every message regardless of its current folder. Starts automatically the moment the account connects (`backfillStatus` defaults to `NOT_STARTED`, which the tick treats the same as `IN_PROGRESS`). Same stale-cursor problem as History API applies to `pageToken` over a sweep spanning hours — same fix: falls back to restarting from the first page rather than getting stuck, safe because `refileMessage` no-ops on anything already correctly filed, so a restart just re-walks already-done mail rather than redoing or undoing real work.
  - Both jobs cap at 20 messages per tick so a big backlog catches up gradually instead of firing one huge AI call. For a large mailbox, expect the backfill to take many hours (or longer) to reach `DONE` — this is deliberate cost/rate-limit control, not a bug; the Mail page shows "Reorganising existing mail..." while `backfillStatus` is `IN_PROGRESS`.
- `src/app/api/mail/{connect,callback,status,labels,messages,activity}/route.ts` — session-protected (belt-and-braces, `proxy.ts` already covers `/api/mail/*`). `connect` starts the consent flow; `callback` is where Google redirects back to, exchanges the code, and redirects into `/admin/mail` with a `connected` or `connectError` query param. `status` includes `backfillStatus` for the UI indicator.
- `src/app/admin/mail/page.tsx` — connect card when no `MailAccount` exists yet; once connected, a three-pane layout (folders, message list, activity feed) plus the backfill-in-progress indicator.

**What's deliberately not built yet:** drafting replies, and any chat/talk panel for asking about the inbox — both explicitly deferred by Morgan on 30 July 2026 pending phase 1 proving out first. Note also that **Talk to Rey already exists** (`src/app/admin/talk`, hosted voice conversation via the Agent SDK pointed at this repo's cloned `vault/`) — when a chat panel for Mail does get built, extending Talk to Rey with a typed mode is the leading option over building a second, separate assistant interface, per the vault's "one Rey, not several" rule. Not decided yet.

**Env vars this feature needs:**
- `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET` — the dedicated "Reyse Mail Assistant" OAuth client's credentials, from the same Google Cloud project as `GOOGLE_CLIENT_ID` above but a different client entry. **Not yet set on Railway as of this build** — required before the "Connect Gmail" button works at all; the connect route fails closed with a plain-language error if missing, rather than crashing.
